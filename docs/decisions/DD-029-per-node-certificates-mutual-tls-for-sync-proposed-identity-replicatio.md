# DD-029: Per-node certificates + mutual TLS for sync (proposed); identity replication opt-in and LWW timestamp admission (implemented)

**Status**: Split. The identity-table question and sender-controlled LWW timestamps are **decided and implemented** (September 2026, security review items S2 and S3; see "Decision: identity tables are node-local unless opted in" and "Decision: LWW timestamps are parsed and bounded at the merge boundary" below). Per-node certificates + mTLS remain **proposed, not implemented**: everything from "Goals" through "Alternatives considered" is the plan to evaluate and, if adopted, implement. This record is the direct follow-on to DD-028's "Revisit if," written up because DD-028 explicitly parked this and the residual risk it describes is the fleet's worst-case blast radius (one compromised node → fleet-wide admin).

**Decision: identity tables are node-local unless opted in (implemented).** The project lead chose "stop replicating by default" over signed mutations for the public release. `admin_users` and `api_tokens`, and tombstones for either table, cross the sync boundary only when a node starts with `SYNC_REPLICATE_IDENTITY=true`. The default is false, and a value that is not a boolean is logged at error level and treated as false. When false, `buildSyncResponse` omits both tables and their tombstones, and `mergeSyncResponse` ignores any that arrive: each ignored row increments `svart_dns_sync_rows_rejected_total{peer,table,reason="identity_replication_disabled"}` and produces one warning per peer per table (not one per row per poll). `GET /api/peers` reports the effective value as read-only `replicate_identity`; it cannot be changed through the API or replicated settings, because a setting that controls whether peers may write admins must not itself be peer-writable. When true, behavior matches earlier releases, plus the row checks the HTTP API applies (role must be `admin` or `readonly`, non-empty username/token prefix and hash) and the timestamp admission below.

*Blast radius, stated plainly.* With the default (false), a compromised or impersonated peer, or anyone holding `SYNC_SECRET` plus the shared wildcard key, can still rewrite every replicated **config** table: upstreams (redirect all DNS to a resolver they control), blocklists and allowlists (including their URLs, see S4), rewrites (answer any name with any IP), ranges, groups, policies and settings, and can delete any of them with tombstones. It **cannot** create, overwrite or delete an administrator or API token on another node, so it cannot turn peer access into login access to the fleet's admin UIs and APIs. With `SYNC_REPLICATE_IDENTITY=true`, the same attacker can also mint an admin (or replace an existing admin's bcrypt hash) on every node that opted in, delete legitimate admins, and add tokens: peer compromise becomes fleet-wide admin compromise, exactly the property described in "Problem" below. mTLS would narrow who counts as a peer, but not what a trusted-but-compromised peer can write.

*Operational cost of the default.* Users and tokens are managed per node. Create the same admin on every node before relying on failover (DD-003's passive node must be loggable-into during the outage window). Password changes, role changes, token revocation and user deletion do not propagate, so revoke on every node. Rows replicated by earlier releases stay where they are; nothing is deleted when the gate closes. Both directions are gated independently, so identity replicates between two nodes only when both opted in; a node with the gate off neither sends nor accepts identity rows even if its peer is on. The homelab two-node deployment must set `SYNC_REPLICATE_IDENTITY=true` on both nodes to keep its previous shared-user behavior, accepting the blast radius above.

**Decision: LWW timestamps are parsed and bounded at the merge boundary (implemented).** Before this change `lww` compared the sender's `updated_at` string with the local one as bytes, and tombstones deleted only rows whose `updated_at` sorted at or below `deleted_at`. A peer could send `9999-12-31T23:59:59Z` or `~` and the row won forever, could never be deleted, and was re-sent on every poll because it sorts after every `since`. Now `admitSyncResponse` parses every incoming row `updated_at` and tombstone `deleted_at` as RFC3339/RFC3339Nano or as SQLite's `YYYY-MM-DD HH:MM:SS[.fff]` UTC form (still present in real databases from `CURRENT_TIMESTAMP` column defaults and `datetime('now')` backfills, and sent verbatim by older peers). Unparseable values (`reason="invalid_timestamp"`) and values more than `maxSyncClockSkew` = 5 minutes ahead of the receiver's clock (`reason="future_timestamp"`) are refused; the tolerance absorbs drift between NTP-disciplined nodes while bounding how long a forged row can outrank a genuine edit, so nodes must keep their clocks synchronized to within that window. Kept timestamps are rewritten to canonical RFC3339Nano UTC, and LWW, tombstone application and tombstone recording compare parsed instants, which also fixes two ordering bugs in the byte comparison (legacy `YYYY-MM-DD HH:MM:SS` versus RFC3339 within the same day, and RFC3339Nano values whose trailing fractional zeros were trimmed). Local values that are empty or unparseable order before every real timestamp, so an admitted write or tombstone supersedes them. The same boundary refuses rows the HTTP API would reject (invalid CIDR or empty name for a range, blank policy name) and tombstones for tables that do not replicate (`reason="invalid_row"`). Refusals do not fail the poll or mark the peer unhealthy; they are counted and logged once per peer per class. At startup, `initSync` runs `repairPoisonedSyncTimestamps`: any row or tombstone that an earlier release accepted with a far-future or unparseable timestamp keeps its content, gets its timestamp set to the current time so edits and tombstones apply to it again, and is logged at error level with table, key and original value. It is never deleted; an operator who finds a poisoned `admin_users` row in those logs should review and delete it deliberately.

**Problem / threat model**: Today's sync trust model (DD-003 for the LWW mechanics, DD-028 for the transport hardening) has three properties that combine badly:

1. **One shared bearer secret for the whole mesh.** `SYNC_SECRET` is a single value stored per node but expected to match across every peer — it's the same string on every box, not a per-node credential. The same is true of the TLS identity: production nodes present the same wildcard `*.example.lan` certificate (DD-028's "Residual trust boundary"), so successful TLS verification proves possession of a key every node already has, not "this is specifically node 2."
2. **All config tables replicate via LWW, including `admin_users` and `api_tokens`.** These carry bcrypt password hashes and token hashes. `mergeSyncResponse`'s `lww()` helper (sync.go) INSERTs a row unconditionally when its natural key (`username` / `token_prefix`) doesn't exist locally yet, and UPDATEs whenever the incoming `updated_at` string sorts after the local one — a plain string compare the sender fully controls. There is no signature or origin check independent of that timestamp.
3. **Sync fans out transitively.** A node doesn't just accept what a peer sends — once merged, that row is now local data, and it gets served forward to every other peer that polls this node next. A single bad row entering anywhere in the mesh reaches every node, not just the two directly-connected ones.

Concretely, this means: if any one svart-dns node is compromised (root on the box, or its local SQLite file is written to directly — which requires no protocol exploit at all), the attacker can insert a new `admin_users` row or overwrite an existing bcrypt hash locally. The next time any peer polls that node, the forged row merges in (new username → unconditional INSERT; existing username → UPDATE wins because the attacker sets `updated_at` to anything in the future). From there it propagates to the rest of the mesh through ordinary, unmodified sync. Separately, because every node shares one `SYNC_SECRET` and one wildcard TLS identity, a leak of either (env var exposure, backup, shell history, or a MITM position that can present the shared wildcard cert) is *also* fleet-wide — there's nothing that scopes "this credential lets you act as node 2" versus "node 5." DD-028 already closed the cruder version of this (on-path impersonation via `InsecureSkipVerify`, secret disclosure in config exports, reflected peer errors); what's left is exactly the case its own "Revisit if" flags.

**Important nuance this doc has to be honest about**: per-node certs + mTLS fix property (1) — they replace one fungible, mesh-wide credential with N distinct, individually revocable ones, so compromising or leaking node 2's key stops letting an attacker act as node 5 too. They do **not**, by themselves, fix property (2) or (3): a compromised-but-correctly-identified node can still forge its own `admin_users` rows and have them fan out to every peer, because nothing today checks a row's content against anything stronger than "which TLS-authenticated peer sent it." Presenting per-node mTLS as "solves the admin-backdoor" would overclaim; it narrows *who* can act as a trusted peer, not *what* a trusted-but-compromised peer can inject. That's why this doc treats "should identity tables replicate at all" as a first-class, separate question below rather than assuming mTLS makes it moot.

**Goals**:

- Replace the single mesh-wide bearer secret and shared wildcard TLS identity with a distinct, individually revocable credential per node.
- Authenticate both directions of every sync connection (today only the server side — the peer being polled — presents a verified cert; the polling client presents none).
- Make compromise of one node's key attributable to that node and revocable without rotating a value every other node also depends on.
- Preserve what DD-003/DD-006/DD-022 already got right: no leader election, all nodes stay peer-equal, sync stays cheap for the actual data volume (a few KB, changing a few times a month), and TLS/sync misconfiguration fails sync closed while DNS keeps serving (DD-028's existing failure mode).

**Non-goals**:

- Not replacing the wildcard Let's Encrypt cert used for the browser-facing admin UI — that's cert-updater/production-TLS territory and orthogonal to node-to-node sync auth.
- Not building a general-purpose PKI product or a CSR auto-signing service. Homelab fleet scale is small (DD-022's own "Revisit if" says mesh overhead matters past ~10 nodes); a manually-run issuance step is proportionate.
- Not, by itself, deciding the identity-table replication question — see the nuance above. mTLS and that question are separable and can land in either order.
- Not replacing `SYNC_PEER_ALLOWLIST` (DD-022). Authorization (which URLs may sync at all) and authentication (proving which node is on the other end) are different concerns; both stay.

**Proposed design**:

*Node identity.* Each node gets its own key pair and leaf certificate — CN/SAN set to a stable per-node identifier (`NODE_ID` or a generated node UUID), signed by a sync-specific CA that is a separate trust root from the public wildcard cert. Keeping the sync CA separate means rotating or revoking it doesn't touch the admin UI's public TLS, and vice versa.

*Cert issuance and rotation.* Mint the CA once; issue one leaf cert + key per node from it (a small script, not a service). Favor short-lived leafs (e.g. 90 days, mirroring Let's Encrypt cadence) over building revocation infrastructure (CRL/OCSP) — a leaked leaf simply expires, and removing a node from `SYNC_PEER_ALLOWLIST` already gives an immediate stop-gap. For delivery, lean on the homelab's existing cert-distribution machinery (cert-updater, NFS-mounted certs) rather than inventing new provisioning tooling — the CA bundle and per-node leaf/key are just more files to land on each box the same way `TLS_CERT`/`TLS_KEY` are today.

For rotation *mechanics*, the repo already has the right pattern to extend rather than replace: `tls.go`'s cert watcher (`currentCert atomic.Pointer[tls.Certificate]`, 60s mtime poll — no fsnotify, because it's unreliable on the NFS-mounted cert paths) hot-reloads the certificate `GetCertificate` serves to inbound TLS handshakes. Today that only covers the *server* side of one listener. mTLS needs a second, parallel path: the sync HTTP client (`newSyncHTTPClient` / `newSyncTLSConfig` in sync.go) currently builds its `tls.Config` once per peer dial with no client certificate at all. A rotating client cert needs its own atomic-swap holder (or `tls.Config.GetClientCertificate` callback, mirroring `GetCertificate`) so the outbound leg picks up a renewed cert the same way the inbound leg does — and the two need to rotate together, since a stale cert on either side of a handshake fails that handshake.

*CA / trust bootstrap.* `TLS_CA` already exists as a client-side `RootCAs` pool for verifying peers (`loadSyncTLSConfig` in main.go). The natural extension is to use the same CA bundle on both sides: as `RootCAs` when dialing out (verify the peer's server cert, as today) and as `ClientCAs` when accepting inbound sync connections (verify the peer's client cert, new). One CA, one config value, two roles.

*Interaction with `SYNC_PEER_ALLOWLIST` and the pairing handshake.* The allowlist (DD-022) is an authorization boundary — which canonical HTTPS origins may participate at all — and stays exactly as-is; mTLS answers a different question (is the connection actually from the node it claims to be) and is additive, not a replacement. Pairing (DD-022) today proves "both sides know the same `SYNC_SECRET`" via role-separated HMAC proofs. With per-node certs, that handshake's job could extend to pin the peer's certificate fingerprint the first time it's seen (trust-on-first-use at the moment of an HMAC-proven pairing, which is a strictly stronger claim than "you knew the secret," since a fingerprint isn't fungible the way a bearer secret is) — or pairing could be retired in favor of operators manually exchanging leaf certs, which is simpler to reason about but loses the one-time-code UX DD-022 was built for. This needs a decision, not just an implementation.

*A real implementation wrinkle worth flagging now:* the admin HTTPS server is one `http.Server` on one TLS listener serving the browser UI, `/api/sync`, `/health`, `/metrics`, and `/docs` together (`server.TLSConfig = &tls.Config{GetCertificate: getCertificate}` in main.go). `tls.Config.ClientAuth` is decided at handshake time, before any HTTP routing happens — there's no way to require a client cert for `/api/sync` but not for browser logins on the same listener without branching in `GetConfigForClient` on SNI (fragile — depends on peers reliably sending a distinguishing `ServerName`, which today is only set via `SYNC_TLS_SERVER_NAME` for IP-addressed peers) or standing up sync on its own port with its own `tls.Config{ClientAuth: tls.RequireAndVerifyClientCert, ClientCAs: pool}`. A dedicated port is the more honest option; it costs one more open port per node.

**Migration path**: A rolling, multi-node fleet cannot flip this atomically, and shared-secret and mTLS need to coexist during rollout.

1. Generate the sync CA and one leaf per node; distribute via the existing cert channel.
2. Ship code where client-cert config (new env vars, or reusing `TLS_CA` for the CA piece) is optional. If unset, a node behaves exactly as it does today — server-TLS-only, `SYNC_SECRET` auth — so a not-yet-upgraded peer keeps working. If set, the node *presents* a client cert but doesn't yet *require* one from peers.
3. Add a readiness signal alongside the existing `sync_tls_ready` (DD-028) — an `mtls_ready`-shaped field per peer — so operators can see when every peer in the allowlist has a valid, verified client cert before flipping anything.
4. Only after every peer reports that readiness, enable a strict mode (e.g. `SYNC_REQUIRE_MTLS`) fleet-wide, so sync starts failing closed for any connection that doesn't present a verified client cert. This is the actual cutover step; steps 2–3 are non-disruptive by design.
5. Decide separately whether `SYNC_SECRET` is retired afterward or kept as a second factor alongside mTLS (belt-and-suspenders is arguably worth doing regardless — removing the secret isn't required to get the identity benefit, and keeping both is cheap once both exist).

This sequencing means the mTLS rollout doesn't need to be bundled with the identity-table decision below — they can ship in either order.

**Alternatives considered**:

- **Keep the shared secret; sign identity-table mutations instead.** Rather than (or before) touching the transport, require every `admin_users`/`api_tokens` row to carry a signature over its natural key, `updated_at`, and hash, made with a per-node key established during pairing; a peer verifies against the sending node's known public key before merging, independent of the LWW timestamp race. This targets the actual backdoor directly and is cheaper than full mTLS, but it isn't free — per-node signing keys still need their own bootstrap and rotation story, so it doesn't dodge the "provision + rotate a credential per node" work either; it just scopes that work to two tables instead of the whole transport. It also shares mTLS's residual limit: it stops a compromised node from forging *other* nodes' rows, not from forging its own.
- **Stop replicating `admin_users`/`api_tokens` at all; manage identity per-node or via a designated primary.** Simplest fix and closes the hole outright — nothing to forge if it doesn't fan out. But it reintroduces real operational cost: an admin created on node 1 doesn't exist on node 2, so during the exact failover scenario DD-003 is designed around (Hypervisor restart, router fails over to the passive node), an operator might not be able to log into whichever node is currently serving. A "designated primary pushes user/token changes one-way to replicas" restores some parity without fanning out attacker-controlled rows fleet-wide, but reintroduces the leader/election machinery DD-003 explicitly chose not to have — even if scoped to just two tables — and makes replicas second-class for user management during exactly the outage window that matters most.
- **Do nothing beyond DD-028 (status quo).** Rejected for this doc's purpose: DD-028 already named this residual explicitly, and it's the single largest blast-radius item left (one compromised leaf node away from fleet-wide admin). Worth a real evaluation rather than leaving it parked indefinitely.
- **Do all three at once** (mTLS + signed mutations + stop replicating raw hashes). Mentioned for completeness as the maximal "defense in depth" option, but flagged as more than a ≤10-node homelab fleet needs today — recommend picking one identity-table alternative rather than layering all of them, absent a concrete second incident that argues for it.

**Open questions**:

- ~~Signed mutations vs. no replication for `admin_users`/`api_tokens`.~~ Decided (September 2026): no replication unless `SYNC_REPLICATE_IDENTITY=true`; see the decision above. Signed mutations remain an option if opted-in fleets need identity replication without trusting every peer.
- Where does the sync CA's private key live, and who is authorized to mint a new node leaf — an operator's laptop, or a secrets-vault entry alongside where `SYNC_SECRET` lives today?
- Dedicated mTLS-only port for sync, or SNI-based `GetConfigForClient` branching on the existing shared listener?
- Does pairing (DD-022) get extended to pin a certificate fingerprint after its HMAC-proven handshake, or does it get retired in favor of manual cert exchange between operators?
- Is "wait out the TTL" (up to 90 days on a leaked leaf) an acceptable revocation story for a homelab fleet, given that removing a node from `SYNC_PEER_ALLOWLIST` is already an immediate, existing stop-gap?
- Should `node_id` — currently a free-text field seeded from hostname/`NODE_ID`, not cryptographically bound to anything — become formally tied to the cert's CN/SAN once mTLS lands, so a row's claimed origin can be checked against the TLS-verified identity that last touched it? This matters most if the signed-mutations alternative is the one chosen.
- Rough effort: this is a multi-day change, not a quick patch — CA/cert provisioning, two independent TLS config paths (client and server) needing coordinated hot-reload, a phased fleet-wide rollout, and a separate decision-plus-implementation for the identity-table question each carry real weight before they compound.
