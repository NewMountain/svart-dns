# DD-028: Verified sync identity and non-disclosure of authentication material

**Release procedure update:** The [bounded production release](bounded-production-release.md) supersedes the historical deployment timing, production rebuild and rehearsal procedure below. Security and runtime requirements remain in effect.

**Decision**: Sync clients must verify both the certificate chain and certificate hostname, with TLS 1.2 as the minimum. IP-based peer URLs remain the transport address so recovery does not depend on synced DNS rewrites. For those URLs, `SYNC_TLS_SERVER_NAME` supplies the DNS identity used for SNI and hostname verification while the connection still dials the configured IP. `SYNC_PEER_ALLOWLIST` independently limits which exact canonical HTTPS origins may receive sync requests or participate in manual add, pairing, and gossip. Invalid TLS identity or allowlist configuration fails sync closed without stopping DNS service.

`sync_secret` and `session_secret` are write-only authentication material. Settings responses, config exports, and replication payloads omit both; config import and sync merge ignore either key. `PUT /api/settings/sync_secret` requires at least 32 bytes and returns acknowledgement only; weak environment or stored values are not activated, while direct `session_secret` updates are rejected. Pairing exchanges mutually verified, role-separated HMAC-SHA256 proofs; the raw secret is never transmitted in the pairing protocol. `/api/sync` accepts only the peer `X-Sync-Key`; admin API credentials are not an alternate route to replication payloads.

For secret state, `/api/peers` reports only the boolean `has_secret`. Its `sync_tls_ready` field requires a strong secret, a usable verified-TLS client configuration, and an observed successful sync for every peer. It is not an on-demand probe, so operators must still require peer `healthy`, an advancing `last_sync_at`, and empty error fields. Peer-controlled HTTP status/application bodies and invalid timestamps are discarded; sync redirects are refused and response sizes are bounded. Errors retained in peer state, logs, and operator responses use local generic descriptions rather than reflected remote text. Replicated `sync_interval` is accepted only from 1s through 1h (empty means the 2s default), preventing a peer-controlled ticker panic. Public `/health` exposes only `status`; the frontend retrieves `node_name` from authenticated `/api/peers`. Public sync metrics use opaque `peer-N` labels instead of peer URLs. Admins can invalidate all browser cookies through `POST /api/auth/sessions/revoke`, which rotates the persisted session-signing key without returning it.

Production release safety is part of this boundary. CI on branches is non-mutating. Pushes to `main`, the daily schedule, and explicit current-main retries run one concurrency-serialized release on the isolated `svart-production` runner. The Action binds a clean source SHA to an immutable `linux/amd64` image digest and holds renewable locks on both nodes. Before each deployment mutation the target creates a code/Compose/prior-image checkpoint, arms a one-hour node-local rollback lease, installs persistent reboot recovery, and proves DNS locally. Blue is verified every minute for 15 minutes while Red serves; its attestation binds the exact container and start time. The same Action promotes that digest, verifies both nodes for another 5 minutes, commits Red only after the strict-TLS, exact-topology, advancing-sync, UDP/TCP DNS, policy, and non-disclosure gates pass, and seals both nodes after final strict proof. Any post-deploy failure restores only the changed node and functionally re-verifies both resolvers. SSH host keys are independently pinned and certificates are never rewritten by the release. The runner remains available for direct Forgejo triggers; Arcane and Prefect are not release orchestrators.

Rollback deliberately excludes SQLite and all data volumes, so releases must remain schema-neutral and the archived prior image can safely reuse current data. After the two observation gates pass, the Action strictly verifies both nodes, seals Blue then Red with exact acknowledgements, and strictly verifies both again. Node sealing first proves the managed Compose override still resolves to the promoted digest and cancels every committed/rolled-back transient rollback unit before deleting its state. It retires the authorized automated rollback checkpoint, archive, lease, attestation, and rollback tag; it does not claim to purge every local layer, original image reference, or registry copy. Repeating the same SHA/digest seal is safe because node sealing is idempotent. Credential rotation remains an explicit incident or hardening operation rather than a routine deployment side effect.

**Why**: A shared secret cannot authenticate a peer if an unverified or attacker-selected TLS endpoint can receive that same secret. Config backups, reflected peer errors, and topology-rich public endpoints also unnecessarily widened the impact of read access. Strict certificate verification, an exact destination allowlist, proof-based pairing, and reduced response surfaces close those paths while retaining IP-based recovery and the operational signals needed by health checks and monitoring. Staged deployment keeps a known-serving resolver available while the hardened boundary is proven on the other node.

**Residual trust boundary**: Both production nodes currently present the same wildcard certificate. Successful verification therefore proves possession of the shared wildcard private key, not the identity of one particular node. This is materially stronger than accepting any certificate, but compromise of that shared key can still impersonate either node.

**Residual metrics disclosure**: This decision removes peer URLs/IPs from sync metric labels and removes topology from public health, but the broader unauthenticated `/metrics` surface still contains client IPs, upstream addresses, and entity/list names used by existing dashboards. That lower-severity monitoring boundary is not silently treated as solved here; it needs a separate authenticated-scrape or privacy-preserving-label design before all public topology disclosure can be considered closed.

**Revisit if**: Per-node certificates or mTLS become practical; either would provide unique node identity and reduce reliance on a shared secret and shared wildcard key.
