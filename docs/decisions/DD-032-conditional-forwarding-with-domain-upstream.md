# DD-032: Conditional forwarding with `[/domain/]upstream`

**Decision**: An upstream entry written `[/lan/home.arpa/]192.168.1.1` (the dnsmasq / AdGuard Home syntax) answers only for the listed domains and their subdomains. The most specific configured domain wins (`[/iot.lan/]` beats `[/lan/]` for `cam.iot.lan`). Every other name goes to the unrestricted upstreams, and a restricted upstream never answers outside its domains, even when it is the only one configured. A disabled restricted entry is as if it were absent. Routing is precomputed into an immutable snapshot on every upstream change, so a query costs one suffix walk over map lookups, and nothing when no routes exist. Upstream strings are parsed and validated at the API (POST and PUT return 400 for malformed entries). Entries that arrive unvalidated through config import or sync are left out of routing with a warning instead of failing on every query. AdGuard's `[/domain/]#` exception form and `[//]` for unqualified names are not supported and are rejected.

**Why**: The syntax used to be parsed and then ignored, so a router entry became one more general upstream. Public queries went to the router, and `.lan`, `home.arpa` and RFC 1918 reverse names leaked to public resolvers. The router owns DHCP (VISION: no DHCP), so the only way its hostnames and local PTR records resolve is to forward those zones to it. Pi-hole and AdGuard users expect this. The other option was to delete the parse, which would leave the local-name leak in place and push users to a rewrite per host, and that can't follow DHCP leases.

**Revisit if**: Users need the `#` exception form, per-client routing, or split horizons that depend on the query type.
