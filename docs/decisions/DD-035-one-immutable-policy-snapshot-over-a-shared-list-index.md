# DD-035: One immutable policy snapshot over a shared list index

**Decision**: All in-memory policy state is one immutable `policycore.Snapshot`, published through an `atomic.Pointer` (`policyState`). It holds the `policycore.Index` (every enabled blocklist and allowlist in one pointer-free index, each distinct rule stored once with the set of lists holding it) and, for every entity of every tier, the list sets it uses with named-policy lists merged in: ranges (sorted most specific first), groups, group memberships by client address, and direct (IP tier) clients. `reloadPolicyState(reason, scope)` is the only way that state changes. It is serialized by a mutex, reads every table in one read transaction on `readDB`, builds a complete snapshot, publishes it and only then bumps the policy cache generation. `reloadEntities` reuses the previous index unless the set of enabled lists changed (a rename copies only the index header); `reloadListContent` streams changed list rows into an immutable update when the caller supplies list identities and their combined previous/current size is at most 50,000 rules; unknown or larger changes stream all rows into a full rebuild. A failed build keeps the previous snapshot and forces the next reload to rebuild all saved content, so an unrelated later edit also recovers the failed publication. It returns and logs the error and counts `svart_dns_policy_reload_errors_total`; API handlers answer 500 "change saved but not applied".

**Why**:

- **Correctness (B1).** State was rebuilt piecemeal by about forty calls to six loaders spread over handlers, policies, config import, sync and auto-refresh. A list refresh rebuilt client and group data but never ranges, so a range assigned while its list downloaded never blocked and ranges served the previous list version after every refresh (`TestRangeServesListLoadedAfterAssignment`, `TestRangeServesRefreshedAllowlist`). With one entry point there is no tier to forget, and a query can never see tiers from different reloads.
- **Memory.** Lists were Go maps (~64 B per domain, scanned by the GC, retaining SQLite row strings), one per list even for domains several lists share, and every reload re-read everything into fresh maps. The index needs about 32 B per distinct rule (80.7 MiB for 3.12M rules from five real lists).
- **Speed.** A cache miss probed every list of every entity at every label and read group names from SQLite (~50 us). Now the name is probed once per query and every entity costs a few word operations (a few microseconds, 3 allocations), so the policy cache default dropped from 800 MiB to 64 MiB (`POLICY_CACHE_SIZE_MB`).
- **Less code.** Blocklists and allowlists shared ~90% duplicated loading and matching code; they are now two kinds of slot in one index.

**Preserved behavior**: `PolicyResult` output is identical to the per-tier engine for every query of `TestPolicyEngineMatchesGolden` (96 digests recorded while both engines ran side by side and agreed). That includes one oddity worth knowing: a hit in a manual (custom rule) list is reported as a custom rule with list ID 0 only at the IP tier; group and range manual lists have always been reported as published hits under their "Manual Block (...)" alias.

**Limits**: at most 2048 enabled lists (every client, group or policy with custom rules owns a manual list); beyond that the rebuild fails with the count and the previous policy stays. Large or unscoped list content changes still rebuild the whole index from SQLite. Small identified changes copy only modified hash partitions, remap compact list memberships by both kind and row ID, and reuse other partitions. Exact, wildcard, exception and complex-rule semantics and size/ID attribution remain unchanged. Deleted memberships become inactive; a full rebuild compacts when physical keys exceed twice max(1024, current rule count), or membership sets exceed max(1024, 16 times list count). These thresholds choose a rebuild strategy and never limit stored rules or history.

**Revisit if**: large refresh rebuild time needs further improvement, manual-list attribution should be uniform across tiers (a deliberate output change), or deployments need more than 2048 lists.

**Measured small-edit update (2026-09-28):** With the same three-million-rule fixture and toolchain, three manual edits changed from 2.3–3.0 seconds to 1–20 milliseconds. Sixty-four hash partitions retain the existing open-addressed lookup; the realistic lookup corpus showed no regression and isolated matcher allocation tests remain zero.
